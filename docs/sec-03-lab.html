Lab: Configure Selective Access

Grant access and watch it cascade

Security Lab Hands-On 20 min
📝 How this lab works

This is a guided exploration of your own OWP training tenant — there is no scripted dataset to follow step-by-step. Work in the security management hub (2.1), grant access, and watch how it cascades. The user names from the recordings (Alex, Mariah, Anna) are examples so you know what to look for; use whichever users exist in your tenant.

What you'll do

  • Open the security management hub and select a user
  • Grant write access to an org and confirm it cascades to underlying management orgs and aligned positions
  • Repeat the grant from the budget-hierarchy (BH) side
  • Copy/paste access rows to another user and push to models
  • Observe how selective access changes what a user sees

1 — Select a user in the security hub

The security management hub in 2.1 is where you manage who can see and do what — all through the UX, writing straight back to the model.

In your tenant, open the security management hub.

Pick a user to work with (recording examples: Alex, Mariah, Anna).

  1. Open the security management hub and locate the list of users.
  2. Select a user and review their current access.
  3. Note that the hub also manages users once added — you can change a user's model role and review or update their access from the same place.
📝 One model role per user

Anaplan allows only one model role per user. You can still modify UX-page access (remove or change pages) to simulate the effect of multiple roles, but the underlying model role is singular.

2 — Grant write access to an org and watch it cascade

This is the heart of selective access: grant once at an org and it flows down automatically. Manual grants would be a "nightmare" for a 40–50k-person org — the cascade is the point.

In your tenant, grant your selected user write access to an org.

Recording example: granting write access to "global sales."

  1. Grant the user write access to an org (e.g. "global sales" in the recording).
  2. Confirm it automatically cascades to all underlying management orgs — even though the org list is stored flat.
  3. Confirm it also cascades to all positions aligned to those orgs.
💡 Flat list, hierarchical cascade

The management org list is stored flat, but 2.1 builds a hierarchical view behind the scenes and cascades the grant down it — to underlying orgs and every aligned position. You grant at one level; the app does the rest.

Quick check

Correct. Despite the flat list, 2.1 builds a hierarchical view and the grant cascades to all underlying management orgs and to every position aligned to them. That automatic cascade is exactly why manual access would be a nightmare for a 40–50k-person org.
Not quite. The right answer is A. Even though the org list is flat, 2.1 cascades the grant to underlying orgs and all aligned positions automatically. It works from the budget-hierarchy side too, and it does not depend on an ALM upgrade.

3 — Repeat from the budget-hierarchy side

The same cascade works from the budget hierarchy (BH), not just the management-org side.

In your tenant, grant access against a budget-hierarchy node.

Recording example: granting against everything under "Operations."

  1. Switch to the budget-hierarchy view and select a node (e.g. "Operations").
  2. Grant access against everything under it.
  3. Confirm it cascades to all cost centers underneath and to the budget positions.

4 — Copy access to another user

There is no dedicated "copy from user to user" button, but you can move access rows by hand and push them across all models.

In your tenant, copy the access rows from one user and paste them onto another.

  1. Select the access rows on your configured user.
  2. Copy/paste those rows onto a second user.
  3. Push to models — this works across all models.

5 — Observe how selective access changes what the user sees

Selective access is not just about who can edit — it governs everything a user is shown.

In your tenant, look at the app as (or on behalf of) the user whose access you changed.

  1. Check the drop-downs — do they now show only the orgs and positions the user can reach?
  2. Check the positions visible in the CPP grid for that user.
  3. Check the transfer targets available to them — selective access governs these too.
🚨 Job levels are foundational

You cannot create new job levels in OWP — the job-level framework is foundational. Create job levels in Workday / your HCM and bring them in. Selective access controls who sees what; it does not let you extend the foundational framework.

Quick check

A customer asks you to create a new job level directly in OWP. What's the right answer?

Correct. Job levels are foundational — you cannot create new ones in OWP. They're created in the HCM (e.g. Workday) and brought in. Selective access controls visibility and edit rights; it does not extend the foundational framework.
Not quite. The right answer is D. You cannot create new job levels in OWP — they're foundational and come from the HCM system. Granting access, switching to the budget-hierarchy side, or copying access rows all deal with visibility, not with adding a job level.

Debrief Questions

  1. You granted write access to one org and it cascaded to underlying orgs and aligned positions. Why is that cascade essential for a 40–50k-person org, and what would the alternative cost?
  2. The management-org list is stored flat, yet the grant still cascaded down a hierarchy. Explain to a customer how both can be true at once.
  3. There's no dedicated copy-user-to-user button, but you copied access rows across models. How would you document this so an admin can repeat it safely?
  4. A customer wants a brand-new job level added inside OWP. How do you respond, and where does that change actually belong?
