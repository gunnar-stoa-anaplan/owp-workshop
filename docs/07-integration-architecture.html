Integration & Architecture

ADO, the UDM roadmap, and closed-loop export

Delivering OWP Method · 6

OWP is built with integration in mind, but the app itself has a narrow job: it needs data in the right structure so its import action can load it. Everything upstream of that — parsing, transforming, scheduling — is a separate concern you handle with whatever tools fit the customer.

Why templates instead of a direct ETL?

A common question: why fill in templates rather than plug straight into SuccessFactors and run the full ETL? You can do the direct integration — data prep is "one of the most-used extensions." But it is not part of the app. It's a separate service or model that parses the customer's one big file into the templates.

The app only needs data in the template structure so the import action works. That's the boundary: get the data into the expected shape, and the app takes it from there.

💡 Sequence the integration

Do proper integration after the app is running and the required data is proven. Get the app working with data first; wire up the automated pipeline once you know exactly what the app needs.

Tools for getting data in

Any tool is fine for the data-prep layer — pick what suits the customer's stack:

  • Workday RaaS export + API
  • Informatica off Snowflake
  • NEO / DataHub
  • CloudWorks for scheduling

Moving every app to ADO

Are the apps built with integration in mind? Yes. Some apps ship with data hubs and some don't, but the direction is clear: "the plan is to move every single app to just use ADO" — the Anaplan Data Orchestrator — as the central inbound conduit.

📝 Roadmap / safe harbor

Moving every app onto ADO is a forward-looking, roadmap direction under Anaplan's safe-harbor caveat. Timing and scope may change.

Closed-loop export back to HCM

The point of planning positions in Anaplan is to get them filled — which means the planned positions have to go back into the HCM system. OWP closes that loop.

OWP ships modules and pages to export positions. The export can be triggered by API, done manually, or scheduled via workflow. Custom export modules are an easy extension with no impact on the app — additive, so they don't threaten the upgrade path.

✅ Do

When a customer needs positions pushed back to their HCM in a specific shape, build a custom export module. It sits on top of the delivered export capability and leaves the core app untouched.

The UDM — Unified Data Model

The Unified Data Model is a roadmap direction for shared metadata across apps. Think of it like Oracle DRM — a shared library of metadata.

Instead of replicating something like a cost-center hierarchy across four or five apps and ADO instances, you hold it once in the UDM and use ADO plus workflow to push it to multiple apps — IFP, OWP, Supply Chain, T&Q — simultaneously. In the presenter's words, "that's where we're moving to."

📝 Roadmap / safe harbor

The UDM is a forward-looking, roadmap item under Anaplan's safe-harbor caveat. It describes the intended direction, not a shipped capability, and details may change.
