Lab: Data Readiness Assessment

Decide whether Northwind is ready to start

Delivering OWP Lab Decision

This is a decision lab. You're the delivery lead on the Northwind Global implementation. Northwind has handed over a picture of what data they have and what shape it's in. Your job is to decide whether they're ready to start configuration — and to be honest with them about what has to be clean first versus what can follow.

💡 Open the Case Study

This lab reasons about Northwind Global. Keep the case-study page open — the data situation table below is drawn from it.

What you'll do

  • Read Northwind's data situation, object by object
  • Decide which OWP objects are mandatory to start and which are non-mandatory
  • Identify the one hard blocker that must be clean before load
  • Make a go / no-go call and name the workstream that goes with it
  • Check your reasoning against the inline Answer Key, then take the debrief questions to the group

Run the assessment

  1. Separate mandatory from non-mandatory. Which objects does the app need present to stand up at all? Think about what CPP and the supervisory-org rollup depend on.
  2. Find the hard blocker. Of the mandatory objects, which one is dirty enough that loading it as-is would break the app? What has to be clean before load?
  3. Decide what can follow. For each non-mandatory object, decide whether Northwind can start without it — and what capability stays incomplete until it lands.
  4. Make the call. Is this a go or a no-go to start configuration? If it's a go, what workstream runs alongside, and what do you tell Northwind about the trade-offs?

📋 Answer Key

Per-object verdict:

  • Position — mandatory; dirty and a blocker. Zombie positions and broken worker links must be cleaned before load.
  • Employee / Worker — mandatory; mostly clean, one duplicate to reconcile.
  • Position → Worker link — mandatory; the hard blocker. Broken links (zombies, an employee with no position) must be fixed before load.
  • Management (supervisory) org — mandatory (half the app); ready, apart from one worker missing a manager link.
  • Job role / job level — mandatory and ready; foundational — bring in from the Workday catalog, don't create new levels in OWP.
  • Compensation — non-mandatory to start; base pay for most, OTE / bonus incomplete. Fake it for dev, load real comp later. Full-cost views stay incomplete until it lands.
  • Skills — non-mandatory; free-text and dirty, but matching is manual anyway. Standardize later.
  • Attrition history — non-mandatory; not readily available, so defer it.
  • Budget hierarchy — needed for WFB but unstructured. Start with a dummy 5-level hierarchy and refine.

Go / no-go: GO to start configuration, with a data-cleanup workstream on positions (close zombies, fix broken worker / manager links) as the long pole. Management org, workers, and job levels are ready. Compensation, skills, and attrition are non-mandatory and can follow — but be explicit with Northwind that until they land, the matching and full-cost views won't be complete. The one hard blocker to clean before load: clean position data and a clean position→worker link.

Ready for the debrief questions — compare your reasoning against the Answer Key above.

Debrief Questions

  1. You called this a go, not a no-go. A skeptical Northwind sponsor asks, "If our position data is dirty, why aren't we waiting until it's clean?" How do you explain starting configuration and cleaning positions in parallel?
  2. Compensation is only partial (base pay yes, OTE / bonus no). What exactly can Northwind not see or do until full comp lands, and how do you set that expectation up front?
  3. Skills are dirty free-text. Why is that non-mandatory to start, and what changes about your advice if Northwind wanted automated skills matching on day one?
  4. The budget hierarchy lives in an unstructured spreadsheet. What does starting with a dummy 5-level hierarchy buy you, and what's the risk if you skip WFB entirely to start?
  5. Name the single hard blocker in one sentence. Why is the position→worker link the thing you refuse to load dirty, when a missing manager link or a duplicate worker you'd fix but not block on?
