Create & Edit Positions

Creating positions and fine-tuning fully-loaded cost

CPP Walkthrough 10 min

Once budgeted positions have flowed into the Continuous Position Plan, the plan actions let HR, Finance, and workforce planners create and adjust positions directly in the CPP. This is where the plan stops being a static budget number and becomes a live, negotiation-aware view of what you are actually going to hire.

Plan actions for positions

The CPP groups position work under plan actions. For creating and editing positions you have three:

  • Create a position — add a single new position to an org.
  • Create many positions — add several positions at once.
  • Edit plan positions (bulk) — adjust existing plan positions in bulk rather than one at a time.

Worked example: fine-tuning fully-loaded cost

Creating a position in the CPP lets you cost it more precisely than the budget side allows. Take a sales rep. Out of the box, the app assumes a fully-loaded cost of $78,000. In this scenario you want to reflect a real offer: a lower base plus an annual bonus.

Add a 10% annual bonus and reduce the base by $5,000 — "Adjust value… minus 5,000" — taking base pay from $80,000 down to $75,000. The bonus then works out to roughly $7,300, and the position is created at about $80,000 fully loaded instead of the $78,000 baseline.

Item Value
Out-of-the-box fully-loaded assumption $78,000
Base pay after "Adjust value… minus 5,000" $75,000
Annual bonus (10%) ~$7,300
Position created at (fully loaded) ~$80,000
💡 Why this matters

The CPP allows more precise, negotiation-aware costing than the budget side. Rather than carrying a flat assumption, you can model the actual mix of base and bonus behind an offer, so the plan reflects what the position will really cost.

Edit OTE in the live app: a 10% annual bonus of 7,815 lifts the 78,147 baseline to 85,962. Exact figures vary by position — the point is the fine-tuning.

Guardrails via dynamic text

Instead of hard action errors, the CPP steers you with dynamic text. When something isn't allowed, the page tells you why in plain language rather than throwing a raw platform error. Verbatim examples:

  • "you don't have write access"
  • "your time to hire is too short for creating a position"

The reason for this approach is candid: "error reporting in Anaplan is not super great." Dynamic-text guardrails give the user a readable explanation instead of a cryptic failure.

The edit queue

A queue exists in editing plan and requested positions, so changes can be worked through in an orderly way. Note that there is no approval queue for creating positions — a queue would need someone to manage it, so requests are routed to the right person through Workflow instead.
