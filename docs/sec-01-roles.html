User Roles & Security Model

Roles, features, and the UX page-security matrix

Security Reference

OWP ships with a security model built around two ideas: who a user is (their role) and what they can see and do (the pages and features they reach). Two slides from the sessions describe this — the user-roles matrix and the UX page-security matrix. Both are delivered out of the box and both are fully customizable.

The user-roles matrix

The first slide (the one the presenter joked "John Pitstick hates") lays out the roles down the left and the feature and functionality buckets across the top. Each cell shows the out-of-the-box access a role has to a bucket — a quick reference for who does what in the app before you tailor anything.

The roles down the left of the matrix are:

Role What they do in OWP
Workforce planners Own the position plan — plan positions, run scenarios, and steward the operational view.
Analysts Analyze positions, costs, and workforce data across the org.
HRBPs HR business partners working positions, workers, and movement for their part of the org.
People leaders Managers who review and act on their team's positions and plans.
Talent acquisition Recruit against open and planned positions coming out of the plan.
Comp & rewards Work compensation on positions and workers.
FP&A Finance planning and analysis — budget, forecast, and cost views.

Across the top of the same matrix are the feature and functionality buckets, and each cell tells you the access a given role gets to that bucket out of the box. It is the fastest way to answer "can this role do this?" at a glance.

The UX page-security matrix

The second slide goes a level deeper. Where the roles matrix is about features, the UX page-security matrix is about pages. It is organized by:

  • Categories — the groupings the UX pages fall into.
  • Pages — the individual UX pages within each category.
  • Which model each page applies to.
  • Per-role access — for example workforce planner, HRBP, and Finance — showing what each role can reach on each page.

As with the roles matrix, everything here is customizable. The delivered matrix is a starting point; you adjust categories, page access, and per-role visibility to match how the customer actually works.

💡 Two matrices, two altitudes

Read the roles matrix for the big picture — who owns what feature. Read the UX page-security matrix when you need the detail — which role reaches which page in which model. Together they define the delivered security posture you then tailor.

One model role per user

Anaplan allows only one model role per user. That sounds limiting, but the UX layer gives you room to work: UX-page access can be modified — pages removed or changed per user — so you can simulate what would otherwise need multiple roles. A user keeps a single model role while their page access is tuned to the exact mix they need.
