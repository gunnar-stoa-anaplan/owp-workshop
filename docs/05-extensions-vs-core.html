Extensions vs. Core Changes

Add, don't change — and keep the upgrade path intact

Delivering OWP Method · 4

OWP ships as a fully functional application — roughly 200 modules of structure, logic, and workflow. When a customer needs something the app doesn't do out of the box, you extend it. The skill is knowing how to extend so you get the new capability and keep a clean upgrade path to the next version.

Rule of thumb: add, don't change

The safest extensions add to the app rather than rewrite it. A new page, a new line item on a system module, a new calculation — these are, in the presenter's words, an "easy extension without changing the core app." Because you leave the delivered components untouched, an upgrade can replace them without touching your work.

✅ Do

Reach for additive changes first: a new report, a new dataset OWP doesn't already carry, a new rule or calculation on top of what's there. Add net-new components; leave the delivered ones as they are.

When you must change the core

Sometimes an additive change isn't enough and you genuinely need to change the core app. When that happens, consult the Anaplan TS team / Delivery Advisor for the most effective, upgradeable way to do it. The goal is to make the change so the app can still be upgraded without breaking your extension.

OWP moves forward on a version path — "today we are 2.1, then we have 2.2, 3.0, and so on." Every core change you make has to survive that path. If it doesn't, the customer is stranded on an old version or facing a painful re-implementation at upgrade time.

🚨 Protect the upgrade path

The point of a core change is to solve the customer's need without losing the ability to upgrade the app later. If a requested change would make future upgrades break the extension, that is a design conversation with Anaplan before you build — not after.

The PATH framework

Anaplan is building tooling to identify what was delivered by the app versus what was customized — the PATH application framework. The idea is that at upgrade time you can tell exactly which components are standard and which are extensions, so you know what needs to change and what can be left alone.

Impact depends on scope

Not every change carries the same risk. What matters is how many things depend on the thing you're changing.

Lower impact

Changing a list that few modules depend on is low impact. Add a line item, add a page, add a calculation that references existing data — the blast radius is small and the upgrade path stays clean.

Higher impact

Changing a core list — such as position or the supervisor / management org — touches a large share of the app. That is a design conversation with Anaplan, not a change you make on your own.

The 60/40 rule: what "fit" really means

Be candid with customers about fit. Out of the box, OWP covers roughly "60 to 70%" of what a customer wants (the presenter also framed it simply as "60%"). The remaining 30–40% is extensions, configurations, and customizations. That's the 60/40 rule — set the expectation early rather than promising a perfect fit.

💡 Frame it up front

Customers who buy an app usually want best practice. The 60/40 conversation is your chance to show where the app already does the job well and where a small amount of extension work closes the gap — instead of treating every gap as a surprise mid-build.

Best practice: big extensions go in a separate model

When an extension is large, build it as a separate model that feeds data into OWP rather than growing it inside the app.

⚠ Cautionary tale

A customer built an entire detailed contractor capability inside OWP on an older version. In hindsight it should have been a separate model feeding data into OWP. Building it inside the app added data, modules, and processing bloat that a separate model would have kept out.

Bad process in, bad out

No amount of extension work rescues a broken process. As the presenter put it, "no Anaplan model or application is going to fix a bad process." Bad data or a bad process in means bad out.

🚨 Lay out change management up front

Because OWP implementations go hand in hand with process change, put change management on the table early — in the sales cycle, at the outset — not once the build is underway. If the customer's process is the problem, an extension won't fix it.

The Delivery Advisor role

The Delivery Advisor is not there to teach partners how to build — "you guys are stronger architects than I am." The role is customer-facing advisory. The Delivery Advisor:

  • Understands the requirement and advises where to build an extension and how to link it into the app.
  • Warns when a requested feature is already on the roadmap, so the customer can prioritize their build effort elsewhere.
  • Flags when a requested core change threatens upgradeability, before it becomes a problem.

There should be a Delivery Advisor for EMEA and one for APAC.
